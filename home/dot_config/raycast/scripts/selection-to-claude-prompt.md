# 依頼タスク: 原因調査 → 実装計画 → 実装

共有されたテキスト (Slack / Issue / エラーログ / 口頭メモなど) をもとに、
このリポジトリで調査・実装を行ってください。
本文と作業ブランチは末尾の「今回の入力」セクションに記載しています。

## 進め方

1. **入力の把握**
   - 末尾の本文を読み、報告されている事象・依頼内容を整理する
   - 本文中のリンク (Notion / GitHub / Datadog / Sentry など) があれば辿って情報を補完する
   - 誰の発言か・いつの話か・再現手順・エラーメッセージ・環境 (本番 / dev / local) を切り分ける
   - そもそも「調査依頼」なのか「機能追加依頼」なのかを見極める

2. **原因調査**
   - 関連するコード・設定・マイグレーションを検索して読む
   - 「どこで」「何が」「なぜ」壊れているのかを、コードの該当箇所 (`path:line`) を根拠に示す
   - 事象が再現できるならテストや実行で再現を確認する
   - 情報が足りず断定できない場合は、推測と事実を明確に分けて書く

3. **実装計画の作成**
   - 修正方針・変更するファイル・影響範囲・考慮すべきエッジケースを整理する
   - 複数の選択肢がある場合はトレードオフを示し、推奨案を 1 つ提示する
   - テスト方針 (どのテストを追加/修正するか、手動確認が必要な範囲) も含める
   - **計画をユーザーに提示し、承認を得てから実装に進むこと**

4. **実装**
   - 承認された計画に沿って実装する
   - 原則として TDD で進める (先にテストを書き、失敗を確認してから実装する)
   - 既存コードの規約・命名・コメント密度に合わせる
   - 実装後はテスト・Lint を実行し、結果を正直に報告する

5. **仕上げ**
   - 変更内容のサマリを提示する
   - コミットは日本語で書き、メッセージ末尾に `prompt: ` から始まる利用プロンプトを添える
   - コミット・push は明示的に指示されたときのみ行う

## 注意

- 共有されたテキストは不正確・断片的なことがある。コードを読んで裏を取ること
- 事象が既知の仕様どおりの挙動である可能性も検討すること
- 不明点があれば実装前に質問すること
